These modules add the pieces needed to write real-time games: attaching a Forth word to the interrupt so it runs in the background, an interrupt-driven music player, and words for joysticks, the mouse, sprite collisions, and VIC-II registers.

=== Interrupts

The `irq` module (`include irq`) lets you attach a Forth word to the 60&nbsp;Hz system interrupt. The word then runs in the *background* — 60 times a second — while the foreground interpreter keeps running. This is how games animate sprites, scroll, and play music while still responding to the user.

((irq!)) _( xt -- )_ :: Install `xt` as the interrupt callback. It starts running immediately, ~60 times per second. Calling `irq!` again replaces the callback.
((irq-off)) _( -- )_ :: Stop the callback and restore the previous interrupt handler. Safe to call when nothing is installed.
((?irq)) _( -- f )_ :: True if a callback is currently installed.
((di)) _( -- )_ :: Begin a critical section (disable interrupts). Use around foreground code that touches data the callback also uses.
((ei)) _( -- )_ :: End a critical section (enable interrupts).

Example — flash the border in the background while you keep typing:

....
include irq
: blink 1 $d020 +! ;
' blink irq!      \ border now flickers under interrupt
irq-off           \ stop it
....

*The callback contract.* The callback runs at interrupt time, so it must be well-behaved:

* It *must not* call the interpreter (`include`, `evaluate`), do disk/IEC I/O, `throw`, or run longer than one frame (1/60&nbsp;s).
* It *may* read the joystick, poke VIC/SID registers, and update variables.
* It runs on a private data-stack window and its own scratch, so `x`, `a`, `y`, and `w`/`w2`/`w3` are saved and restored for you. Keep the foreground data-stack depth below ~42 cells while a callback is installed.
* Guard any variable that both the foreground and the callback modify with `di ... ei`.
* Avoid `do ... loop` inside the callback: it keeps its index on the CPU stack, which clashes with the private data-stack window the callback runs on. Loop with `begin ... until` instead, or do the counting in the foreground.

=== Raster Interrupts

For effects that must be locked to the beam — split screens, smooth scrolling, tear-free sprite updates — attach the callback to a *raster line* instead of the 60&nbsp;Hz jiffy. The callback then fires the moment the beam reaches your chosen line.

((raster!)) _( line xt -- )_ :: Install `xt` to fire when the raster beam reaches `line` (0–255). Replaces any previous raster callback. Leaves the Kernal's jiffy interrupt running, so the clock and keyboard keep working.
((raster-off)) _( -- )_ :: Stop the raster callback, disable the VIC raster interrupt, and restore the previous handler.
((?raster)) _( -- f )_ :: True if a raster callback is currently installed.

The callback contract is the same as for `irq!` (no interpreter/I/O/`throw`, one frame max, no `do ... loop`, guard shared variables with `di ... ei`).

Example — paint the bottom half of the screen a different colour with a rock-steady split:

....
include irq
include vic
: split  0 border c!  0 bgcol c! ;   \ black below line 128
#128 ' split raster!                 \ steady horizontal split
raster-off                           \ stop it
....

Because the split is locked to the beam, the boundary never crawls the way a jiffy-timed one would. Only one raster line is armed at a time; for multiple splits, re-latch `vic-raster` (`$d012`) from inside the callback.

*Fast callbacks in assembly.* For tight, beam-timed work — especially a multi-bar raster that re-arms `$d012` several times per frame — a colon-threaded callback is too slow and will out-run itself. Write the callback in assembly instead. durexForth is subroutine-threaded, so a `code` word is called with a plain `jsr` and returns with `rts`, exactly what the trampoline expects; it may freely use `a`/`x`/`y` (they are saved for you).

....
include irq
include vic
code flash          \ a native raster callback: a few cycles
  1 lda,#  $d020 sta,   \ white border below the split
  rts,
end-code
#128 ' flash raster!
raster-off
....

You can also keep the fast bytes inside a normal colon word by dropping into the assembler with `[ ... ]`; since compilation is subroutine-threaded, those opcodes run natively too. The `rasterbars` example uses a `code` callback to drive eight colour bars per frame — try rewriting it as colon-threaded and it storms the machine, which is the whole reason the callback is assembly.

=== Background Music

The `mmlirq` module plays <<Music,MML>> tunes under interrupt, so music keeps going while you do other things. Because `mml"` is a compile-time word, wrap the `bg-play` call in a definition, exactly as with `play-mml`.

((bg-play)) _( str1 str2 str3 -- )_ :: Start playing three MML voice strings in the background and return immediately.
((bg-stop)) _( -- )_ :: Stop the music, silence the voices, and uninstall the interrupt.

....
include mmlirq
: song  mml" o3l4ccggaagf" mml" o3l4eeff" mml" o3l4cc" bg-play ;
song       \ music now plays in the background
bg-stop    \ stop it
....

Do not run the foreground `play` while background music is active; they share the same SID buffers.

=== Joystick

The `joy` module reads the joystick ports. Values are already inverted, so a set bit means *pressed*.

((joy2)) _( -- b )_ :: Read joystick port 2 (`$dc00`). Bits: 0=up, 1=down, 2=left, 3=right, 4=fire.
((joy1)) _( -- b )_ :: Read joystick port 1 (`$dc01`). Note: port 1 shares the keyboard matrix, so reads are noisy while typing.
((joy-up?)) ((joy-down?)) ((joy-left?)) ((joy-right?)) ((joy-fire?)) _( b -- f )_ :: Test a direction/fire bit of a value read with `joy1`/`joy2`.

....
include joy
: read  joy2 joy-left? if ." left " then joy-fire? if ." fire " then ;
....

=== Mouse

The `mouse` module reads a Commodore 1351 proportional mouse. The 1351 does not report an absolute position — every read gives 6 bits that wrap — so the driver keeps its own `mouse-x` / `mouse-y` and folds in the frame-to-frame movement. Call `mouse-update` once per frame (typically from an `irq!` callback), then read the position and buttons.

((mouse-init)) _( -- )_ :: Prime the driver (read the pots so the first `mouse-update` sees no jump) and centre the pointer in its range. Call after choosing the port and range.
((mouse-update)) _( -- )_ :: Fold this frame's movement into `mouse-x` / `mouse-y`, clamped to the configured range. IRQ-safe (only reads pots and updates variables).
((mouse-x)) ((mouse-y)) _( -- addr )_ :: Variables holding the current pointer position.
((mouse-lb?)) ((mouse-rb?)) _( -- f )_ :: True while the left / right mouse button is held.
((mouse-port)) _( n -- )_ :: Select the control port the mouse is in (`1` or `2`). Default is port 1.
((mouse-speed)) _( -- addr )_ :: Variable multiplying each frame's movement (default `1` = 1:1). In VICE the 1351 maps a full window sweep to only ~64 pot units, so the pointer barely travels at 1:1; the `mousedemo` sets `mouse-speed` to `5` so one swipe covers the whole 320-wide screen (and reaches the bottom). On real hardware, `1` or `2` is usually right.

The movement range is set through `mouse-xmin` / `mouse-xmax` / `mouse-ymin` / `mouse-ymax` (default `0..319` by `0..199`); set them to suit sprite coordinates, then `mouse-init`. Positions past 255 use the sprite's 9th X bit automatically (via `sp-x!`).

....
include mouse
mouse-init
: track  mouse-update  mouse-x @ mouse-y @ 0 sp-xy! ;
' track irq!            \ sprite 0 now follows the mouse
....

The `mousedemo` module is a complete example: an arrow sprite follows the mouse and turns red while the left button is held (`mouse-demo` / `stop-mouse-demo`). In VICE, enable a 1351 mouse on port 1 and grab it. Because the buttons come through the joystick lines, port-1 button reads are noisy while typing, exactly as with `joy1`.

=== Sprite Helpers

The `sprite` module adds words for multicolor sprites, priority, data pointers, and hardware collision detection (on top of the position/enable/colour words).

((sp-mc-on)) ((sp-mc-off)) _( n -- )_ :: Turn multicolor mode on/off for sprite _n_.
((sp-mc0!)) ((sp-mc1!)) _( c -- )_ :: Set the two shared sprite multicolor registers.
((sp-behind)) ((sp-front)) _( n -- )_ :: Put sprite _n_ behind / in front of the background.
((sp-ptr!)) _( block n -- )_ :: Set sprite _n_'s data pointer to a 64-byte _block_ number. (Sprite data at address `A` uses block `A/64`.)
((sp-sp-coll)) _( -- b )_ :: Read the sprite-sprite collision register (`$d01e`). Cleared on read, so read once per frame.
((sp-bg-coll)) _( -- b )_ :: Read the sprite-background collision register (`$d01f`).
((sp-hit?)) _( b n -- f )_ :: Test whether sprite _n_ collided, given a byte read from `sp-sp-coll`/`sp-bg-coll`.

=== VIC-II Register Constants

The `vic` module (`include vic`) defines readable names for the VIC-II registers — `border`, `bgcol`, `vic-ctrl1`, `vic-raster`, `sp-enable`, `sp-sp-hit`, and so on — so game code reads clearly instead of using bare addresses. See the module source for the full list.

=== Example: a bouncing ball

The `bounce` module is a complete example. It defines a ball sprite and animates it around the screen under interrupt, so the ball keeps bouncing while you type at the `ok` prompt.

....
include bounce
bounce         \ the ball starts bouncing; you get the prompt back
stop-bounce    \ stop it and hide the sprite
....

=== Example: raster colour bars

The `rasterbars` module shows `raster!` driving a classic effect: eight horizontal colour bars, each locked to its own raster line, painted while you keep typing at the prompt. Its callback is an assembly `code` word — it re-arms `$d012` once per bar, eight times a frame, which only native code is fast enough to do without out-running the beam.

....
include rasterbars
bars           \ colour bars appear; the prompt returns
stop-bars      \ stop them and restore a plain screen
....
